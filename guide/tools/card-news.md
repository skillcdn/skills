# Card-news skills

How the skills that make card news (`instagram-card-news-format-study` and `html-card-news-from-brief` in the design area, `web-card-news-topic-brief` in the product area, and `html-design-variations` for a format of the user's own) are written and kept in step, for authors. They drive three tool families (a website read with a driven browser, the open web, HTML rendered by a headless browser), so what they share is not a tool but two artifacts: the document set [`docs/card-news/`](../../docs/card-news/README.md) holds the shape of each, and this page says what goes there, what stays in a skill, and how the three are tested together.

## Four skills and the seams between them

The run these skills come from was one job in the user's words ("make a card-news post the way that account does it") and three jobs in the evidence: a study of the account, a research of the story, a build of the slides. Each is written as a skill that is complete alone and useful alone (a study of an account's format, a sourced brief for any post, a build from any brief), and the seams are written in the skill that needs the other's result: the build says where its spec and its brief come from and what it does with neither; the study and the research stay general. The study and the build are design skills, because a format is measured and followed and a render is checked, and the research is a product skill, because a brief keeps evidence apart from inference; the set sits at the root `docs/`, included by all three, since the format serves a page to skills of two areas only from there.

| In `docs/card-news/` | In the skill |
|---|---|
| `format-spec.md`: the fields of the spec, how each is measured and how the build reads it, and the ways to a spec when the reference's site is walled from the host, which apply the browser set's `walls.md` to a format | How posts are read on the site, which posts, the slide log, the verdicts of the study |
| `topic-brief.md`: the fields of the brief, how each is obtained and how the build reads it | How candidates are searched and ranked, the facts table, the angle test, image sourcing from where the articles point (their photos, a cited clip's frames, the subject's pages, a search last), legibility |
| | The script's checks, how the spec's slide types become the page's classes (the build has no catalogue of its own), the page, the server and export scripts, the review |

The test for a sentence: would the next skill that writes or reads a spec or a brief need it? Then it belongs in the set. Everything about one skill's method stays in that skill, because each may be mounted alone or copied.

## What the user corrected, and where it went

The run was sent back five times, and each correction is a rule in the skill whose phase it bears on, with the reason beside it: the density of a slide (counts, not impressions; the study measures them, the build keeps them), the thread (one thesis, text only where needed), the sourcing (every sentence to an article sentence; the angle published and quoted), the register (patterns with wrong-sounding counterparts, checked sentence by sentence), and the layouts (chosen by content, never a sequence repeated where the account varies). A later run on an account that stacks broadcast frames whole added three more: the layouts are the spec's own slide types and nothing of the skill's (a build composed from a catalogue of the skill's own, with the spec only adjusting it, was sent back twice as "not the format", so the catalogue went and the spec's types became the only classes); the images show the story, from where the articles point (the articles' photographs showed nothing of it, the broadcaster's clip they cited showed all of it); and every image is judged legible at phone size before it is placed (slides on blurred frames came back as "this cannot be seen"). A request for a format of the user's own (a new magazine with no reference, or a reference changed a little or wholly) then found the skills able only to reproduce a measured account, and the variation set had settled a card news look as having no producing skill; the spec gained a second source, designed by the design variations from a measured spec at the user's pick, with the routes in `format-spec.md`, and the build holds to whichever spec it is given. Two posts built on formats measured from a genre came back as "too much text": the density stays the genre's measured counts unless the user asks, and then the build cuts within the spec's ranges or the variations move density as an axis and the designed spec carries the chosen counts; a skill never lightens a measured format on its own. A partisan readership then asked for a far more aggressive post with rumors in it: the stance, the tone and the rights handling became the user's to set, asked once with the readers and kept in the brief, while the floor stayed (every claim attributed, an unverified item off the slides), so that the skills serve a side's magazine without printing what no one reported. Fresh sessions given a request with no reference then recommended a format of the user's own every time, because the routes were listed by what the user wants and not by preference (2026-10): the routes are now offered in a fixed order, the reference varied first and the reference as it is second, the build asks for the reference before it offers a route, and the study finds candidates when the user has none, so that a design from nothing is the last offer, said so. A future run that meets a correction of the same kind sharpens that sentence rather than adding a note.

## Facts are dated, and instance material stays out

The site a study reads has no changelog: a statement about what is visible without signing in, how a carousel is stepped, or how a host's browser behaves carries the day it was checked and the way to find it again (what the site does in `docs/instagram/`, what a host's browser does in `docs/browser/`). The build skill carries no layouts of its own: the spec's slide types are its classes, and its one stand-in page for a build with no spec (`no-spec.md`, not included, read only then) is said to be a stand-in at every checkpoint. No account, outlet, story, person or photo from a run is named anywhere in these skills or in the set: examples use placeholders, numbers quoted from runs are shapes.

## Testing

Each skill is tried alone from a fresh session, and the three together with one request that needs all of them ("make a card-news post about <a stand-in topic> the way <a stand-in account> does it") at least to the build's plan checkpoint; a request that names no reference ("card news for our new magazine about <a stand-in topic>") tries the route through the design variations the same way. What a fresh agent had to guess goes back into the files; a site that behaved differently changes the sentence in the study's tool notes, with the day; a finding about a field of the spec or the brief changes the shared page and the skill that writes it in the same change.
