# SkillCDN skills

How the skills that work on a repository in the SkillCDN Format (`skillcdn-…`) are written and kept in step, for authors. What they share at run time is the document set [`engineering/docs/skillcdn/`](../../engineering/docs/skillcdn/README.md), which agents read; this page says what goes there, what stays in a skill, and how the family is tested.

## The tool is the repository and its service

The skills drive a checkout (git, Node.js and the repository's own check), the SkillCDN connection to the same repository, and a way to start an agent with none of the session's context. They name the connection's tools by their exact names (`browse_repo`, `search_repo`, `load_skill`, `read_repo_file`, and `search_packs` at a deployment's root) and the rest as capabilities (a shell, a subagent tool, a second session the user starts), because every host names its subagent and shell tools differently and changes them; a host's tool name appears only as a dated example.

## What is shared and what stays in the skill

| In `engineering/docs/skillcdn/` | In the skill |
|---|---|
| `serving.md`: the default branch, the served commit and how to see it, how long serving takes, what each way of receiving a skill brings, the two checks | When the skill pushes, what it confirms first, what it checks before a commit |
| `fresh-agents.md`: what fresh means and what still reaches an agent, a subagent, a second session, its stops | The brief's request, what the agent is asked to report, how its stops are answered |
| `transcripts.md`: where a host keeps a session's record and memory, their shape, reading them as data | What is taken from them: the evidence sheet, the run record |
| `searching.md`: what a search does and how it ranks, the words that match, what to change when a search finds nothing, reading what was found | The frame, how many searches end a question, what is read before a quote, how a finding is cited in the delivery or in the note |

The method both skills use to test a skill (the dry-read brief, reading a run, where a finding goes, the rounds) is written in each: the authoring skill's `references/testing.md`, and the verification skill's `references/dry-read.md` and `references/fresh-run.md`. It is the skills' workflow, which stays inside each so that a skill mounted alone or copied still has it; a change to it in one skill is made in the other in the same round.

The set sits in the area's `docs/` because every skill of the family is an engineering skill: it travels with the engineering mount and plugin, and each skill's Requirements end with the one sentence on where a route that lacks a linked file reads it. The test for a sentence: would it be true in the next skill that works on a repository in this format? Then it belongs in the set. A page of the set is reached by a root-relative path. The verification skill reads `serving.md` and `fresh-agents.md` from its first two phases on, in every run, so it includes both; the authoring skill always runs in a checkout and includes nothing, reading each of its references and both pages at the phase that names them; the document-pack skill reads `serving.md` at its push; the two reading skills follow `searching.md` in every search and include it; `transcripts.md` is read at the phases that link it. The indexer's check prints each skill's includes, so this paragraph says when a page is read and the check says what is included. A change to an included page changes the served digest of every skill that includes it, as a change to a manifest does, and a push that touches none of a skill's sources leaves its digest as it was: edit an included page deliberately.

The set's pages and the skills name the standard's pages by skill URI (`skill://gh/skillcdn/skillcdn/docs/specs/...`), with the git host's address beside it where a person reads the page, never by a restated sentence with a version, which goes stale without anyone touching it. `npx @skillcdn/cli@latest check --references` asks whether each such file is still there.

## Facts are dated

A host's paths, tool names and limits, and the service's endpoints and timings, change without notice. A sentence that states one names its source and the month it was checked; a sentence about how the service works carries no date. When a run finds one wrong, the sentence changes ([skill-authoring.md](../skill-authoring.md) "Knowledge pages").

## Examples name no one

Paths, sessions, addresses and requests in the set and the skills are placeholders (`<slug>`, `<session id>`, `<address>`, `<path>`), apart from this repository's own address and paths. No run's subject, person or customer, and no path of anyone's machine.

## Testing

The authoring skill is exercised by making a skill from a job and having its fresh agent run it; the verification skill by verifying a skill that is already served, with a request that costs nothing to run where one exists, to the end. A release of SkillCDN or of the console is a change under every skill of the family at once: the verification skill's release review reads the changelog and the spec diff against every sentence of the set and of the skills that states how the service behaves, folds each in with the version and the month, and runs the skill the release changes most; the first release reviewed this way, 0.4.1, moved the originals and the pictures of a document pack into the format and the format's hygiene rule to the repository's visibility, which changed the document-pack skill's layout and its rule on what stays out. The second, SkillCDN 0.5.1 with the console 0.5.0, brought derived documents with checked quotations, section fragments in links, the layout of a long original, a lighter skill boost in the ranking and identifier queries matched as written, which changed the three document skills and the searching page; the console left the sentence a bound checkout carries as it was and raised both version floors to 0.5.0, which added the exit-4 outcome to the root rule. A later one, SkillCDN 0.5.3 with the console 0.5.2, changed two texts an agent is handed, the connection's folder lines, which now share the room and lose words before a folder is left out, and a skill's pages, which end after a line, with later parts that do not say the skill's facts again; and how a search reads a name joined by capitals, by its words where it names something (reading rules version 19). It changed sentences of the searching and serving pages and of the authors' pages and no step of a skill of this family; the search examples of `guide/finding.md` returned the same under the new rules; and the console's release left the sentence a bound checkout carries as it was, while its new setup of an agent account's machine reached the desk skill (`guide/tools/git.md`); the run that followed, of the question-answering skill on a public pack with a question on a name joined by capitals, met nothing the tools did differently from the pages. The fourth, SkillCDN 0.6.1 with the console 0.6.0, brought pages that end between two blocks of Markdown and say how many follow, the check's `context:` line and its note on a large skill, a manifest's `start`, links to another pack by skill URI with `check --references`, `skillcdn catalog`, and a served digest that follows the content alone; it rewrote `serving.md` and `searching.md` to what a skill acts on and moved the authoring skill's references out of its includes, and no fresh run followed it. The fifth, SkillCDN 0.6.2 with the console 0.6.1, kept what waits for its embedding where its words place it, bounded a command's reads in bytes, with a part of a skill that ends in the command for the next, and noted in the check the skills served as a long document; the console gave an agent account a browser of its own, let a command's own sign-in stay in the system's keychain and told a person of nothing they had not turned on. The session that made the first release had folded it into `serving.md` alone, and the review found the same fact stale in `searching.md`, the route through a console's command in `docs/pack/finding-a-skill.md` written to sizes and words the release changed, and a command in the README that no one had run (an account named without its sign, a task left an idea). A fresh reader given the changelogs and the spec diffs found ten sentences of the fold-in that said more than the sources and three stale ones the session had passed; the mode is now its own page, and the skill gained the pack review. The document research and the question-answering skills are exercised on a pack that is public, with a question in the pack's language, one in another, and one the pack does not answer, and the citations are opened. A change to any of them is dry-read before it is pushed. A run is read against the files as the verification skill's `references/fresh-run.md` says; what a host or the service did differently goes into the sentence of the set it bears on.
