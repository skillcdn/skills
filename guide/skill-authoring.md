# Writing a skill

The format is not defined here. It is the [SkillCDN Format](https://github.com/skillcdn/skillcdn/blob/main/docs/specs/skill-repo.md), specified in the SkillCDN repository: what `SKILL.md` and `SKILLCDN.md` are, which front-matter fields exist and their limits, how names are validated, what is served and searched; its own pages for authors are [writing skills](https://github.com/skillcdn/skillcdn/blob/main/docs/guide/write-skills.md), [writing a pack](https://github.com/skillcdn/skillcdn/blob/main/docs/guide/write-a-repository.md) and [writing documents](https://github.com/skillcdn/skillcdn/blob/main/docs/guide/write-documents.md). If this page and the spec disagree, the spec wins and this page gets fixed. This repository is the spec's reference repository, so it follows every required point and every recommendation.

This page adds what this repository asks on top of the spec, and how to write the body.

## What this repository adds

- Every skill lives in an area: `<area>/skills/<name>/`. The area's `SKILLCDN.md` says who its skills are for and adds the rules they share; a skill inherits both and restates neither.
- Prefix the skill name with the tool family it drives (`higgsfield-…`, `github-…`) so related skills sort together, and hyphenate every word of the name (`card-news`, not `cardnews`): search matches a name by its parts, and a match in a name counts twice a match in the body. The directory name is the skill name.
- A skill carries what it cannot work without, because it may be mounted alone at `.../skills/<area>/skills/<name>`, installed as part of the area's Claude Code plugin, or copied into another agent: its workflow, checkpoints, verdicts and hard rules link only inside its own directory. What the skills of one tool family share lives once in `docs/<family>/` (in an area's `docs/` when every skill that includes its pages is in that area) and is reached by a root-relative path (`/docs/<family>/<topic>.md`): the page every run needs is declared in `skillcdn.include` and arrives with the skill wherever SkillCDN serves it, which the format does for a page of the root's `docs/` or of the skill's own area's; the rest, and any page of another area's documents, are linked from the phase that reads them and read through the repository connection, since one person runs the skills of every area together; the Requirements say which pages a plugin install, a copy or a mount below the root lacks and where to fetch them. `node scripts/check.mjs` rejects any other include or link that leaves the skill directory.
- A skill does not restate the rules of the repository or of its area. They are the bodies of the `SKILLCDN.md` files above it, and SkillCDN hands them to the agent before the skill's own body. A skill's own hard rules cover what is specific to it; where a shared rule takes a specific form in the skill (which step costs money, what is confirmed before it), the skill states that form, so that it stays safe when it is copied or installed without SkillCDN.
- A handover is written in the skill that needs it. A skill that can start from another skill's result says where that input comes from when the user has none, how it chooses among what the other skill returns, and what it takes over; it names the other skill in a sentence and does not restate its method. The skill that is used stays general: it says what it delivers and is not narrowed to one use of it. A skill mounted alone still works, and says what to add. How such a run goes is the root rule "Skills chain" (the other skill first, on the user's word, at its own stops, its result taken as the user's input); the skill says only which skill, and what it takes over.
- No rendered media, screenshots or generated output. Skills ship text. Data an agent must read is small JSON in `assets/`.
- Public hygiene is this repository's own rule, beyond the format's. The format asks only that a public repository hold nothing that is not for everyone, since the repository's visibility is what decides who reads a pack (its required point 7, from SkillCDN 0.4.1); this repository also keeps out real people's identity and likeness, customers' material and anything a run's subject could be found by (`CLAUDE.md`, rule 2), because its skills are examples that anyone forks.
- `license` is `MIT` unless stated, and it decides whether SkillCDN serves the skill in full or only describes it: keep it a license the indexer recognizes as permissive. `metadata.tools` names the tool family. Quote a `version` so it stays text, and keep `metadata` flat.
- What SkillCDN adds to the front-matter lives under `skillcdn`: `include` lists the files every run needs, the skill's own relative to its directory and a shared page under `docs/` by its root-relative path, so that `load_skill` and the MCP skills extension return them with the skill (the rest stay linked from the phase that needs them and are read when it comes); `translations` carries a `title` and a `description` per language tag for people who read the page in that language. The `name` and the `description` stay in English, the language the root manifest declares; agents read those. The `skillcdn` key stays in the source: the `SKILL.md` a host receives is re-serialized without it, with the rules and the included files inside, so what arrives is a plain Agent Skills document.
- Size: the body and the included references together stay around 16 KiB of text. `load_skill` pages the context at that size, and the rules of the repository and of the area come first on the pages. Material only some phase needs is linked from that phase, not included. The skills extension lists a skill only when a host can hold it whole (the directory named after the skill, at most 512 files and 16 MiB in all); the `check` role prints whether it is listed and, if not, why.

## Body skeleton

The spec recommends the order from a summary through requirements, inputs and the workflow to the hard rules and the terms; every `SKILL.md` here follows it with two sections of its own, so an agent that has read one knows where to look in the next:

1. **Title and one-paragraph summary.** What comes out, from what, and why the skill works the way it does, in the words a run's user used.
2. **How the user is involved.** Four bullets, always the same: *Questions*, what is asked and in which words, only when the request leaves it open; *Checkpoints*, where the run stops and what the message holds; *Go-ahead*, what "go ahead alone" skips and what it never skips (a spend, what leaves, the user's own pick); *Changes mid-run*, which phase a correction re-enters at, written from the corrections runs met ("too much text" re-enters at the plan, for every slide).
3. **Requirements.** A table of what the skill calls and what each is for, then what to check before the first message and what to do when something is missing; then the paragraph on the shared pages: which pages of a `docs/` set are included and arrive with the skill, which are only linked, what a copy, an area plugin or a mount below the root lacks and where to fetch them, naming this repository; and, where a rule of the area takes a specific form in this skill, that form in a sentence.
4. **Inputs.** A table (input, source): what the user gives, what is asked when it is missing with the question's wording, and "Everything else", derived and shown at the first checkpoint.
5. **Workflow.** Numbered phases, each producing a named artifact the next phase reads, with its checkpoint written as the message the user sees and the word that continues. Anything longer than a paragraph goes to `references/` and is linked from its phase.
6. **Verdicts.** A table (result, verdict) read before the costly step or the review: what is accepted, accepted with a change, or redone, and how many times.
7. **Hard rules.** The short list an agent must never break, each with its why, so it can be re-read before every costly step.
8. **Terminology.** The words the skill uses with a fixed meaning.

## Style

- Write for an agent with no memory of the previous session: current facts and decisions, not history.
- Imperative mood, short sentences, one idea each.
- Name a tool by its exact tool name in backticks the first time; describe it in words after that. Where the tool is a capability that every assistant provides under another name (a browser it can drive, a shell), name the capability and say how to recognize it: a product's tool names do not carry over to the next agent or outlast the next release.
- Do not pin versions of models, products or APIs. Tell the agent to discover the latest through the tool's own catalog, and say how to choose when several qualify.
- Where a number matters (a limit, a cost), say how to obtain it at run time. A dated snapshot may illustrate the shape, clearly marked as such.
- Decision points get a table: condition, choice, why.
- Anything the agent must ask the user is written as the question to ask.
- The `description` field is what search ranks first, and the whole of what a client sees of a skill before it loads it: the connection's instructions quote none of it (only the root's and each area's), a `browse_repo` listing shows its first 240 characters and a search result its first 360 (SkillCDN 0.4.1, checked 2026-10). Its first sentence says what comes out from what, in the nouns a user would say (the job, the input, the result, with their common synonyms); the second begins "Use when" and quotes the user's own phrases, formal and casual, so that a listing cut short still says when; then which skill of the pack its input comes from and which takes its result, where one does, and which neighbouring skill to use instead where their purposes overlap; then how, in a clause or two; and what it costs where that is nothing ("Nothing is spent."). The `translations` description says the same in the other language and changes in the same edit. Every skill also has a section in `docs/pack/jobs.md`, the index an agent searches first; `scripts/check.mjs` fails without it.
- `metadata.version` is quoted text, "1.0" for a new skill; a change that alters what an agent does in a run (a step, a stop, a verdict, a rule, a value it uses) raises the minor number, and a change of wording alone leaves it. The skill's row in `guide/roadmap.md` says what a fresh run reached at that version and what stays untried.

## Knowledge pages

A page that holds what skills know about a tool (a skill's `references/tool-notes.md`, or a page of `docs/<family>/`) is organized by topic and says what holds now, so that an agent finds a fact where it would look for it, not where it was learned.

- One section per topic, in the order a run meets them, each heading naming its topic in the words an agent would search with: a search result names the sections that matched, and `browse_repo` outlines a page by its headings. A procedure in the imperative, a fact as a statement. No chronological sections, no run narratives ("second run", "first production"), no changelog.
- A fact that can go stale (a price, a model's roles or quirks, a render time, a limit read from a tool's description) names the model or the source it was seen on and the month it was checked, at the end of the sentence: "(Seedance 2.5, checked 2026-10)"; a website that changes without notice gets the day, and next to it the way to find the value again. A fact about how the tool works carries no date; when a run finds it wrong, the sentence changes.
- The evidence that makes a fact credible (a number, an error text, what the decoders wrote) goes into the sentence it supports, as a clause. What a run taught replaces or sharpens the sentence it bears on; it is not appended.
- A number that illustrates a shape is marked as illustrative; the run's own measurement is the number.
- What a run produced (its product, persona, lines, story) stays out; the behavior goes in.
