# A first-draft deck in HTML and PDF from an outline

A content outline goes in: the slides the deck should have, with the words that go on each, in any shape the user has them (a meeting plan, a document with a section per slide, notes in chat). Out come one deck file (JSON, one slide after another, each a type and its blocks), one self-contained HTML file in which every slide is one 16:9 page, one PDF printed from it, and a contact sheet the agent has looked at. The deck is a draft for a designer or for the user to present as is: the structure, the wording and the order are final, the visual polish is not. Nothing is generated by a model and nothing is spent; the only tool beyond the shell is a browser that prints to PDF.

## How the user is involved

- **Questions:** only for the outline and, when the deck is for people outside the organization, for the house style (the words and characters the organization bans in external documents) when neither the request nor the organization's files say. Everything else (the slide types, the blocks, the tokens, the file names) is derived and stated.
- **Checkpoints:** the slide plan (one line per slide: its title and its block types) before rendering, and the contact sheet after. Each is one short message; "OK" continues. The plan checkpoint is skipped when the outline already names a block per slide.
- **Go-ahead:** when the user says to go ahead alone, both checkpoints are skipped; the delivery still shows the contact sheet and names what the agent fixed after looking at it.
- **Changes mid-run:** a wording or order change goes into the deck file and the deck is rendered again; the HTML and the PDF are never edited by hand.

## Requirements

| What | Used for |
|---|---|
| A shell with Python 3 | The helper `scripts/render.py` in this directory renders the deck file to HTML and prints the PDF. The skill works without it: [layout.md](references/layout.md) gives the page geometry and the markup of every block, enough to write the HTML by hand. |
| A Chromium-family browser the agent can drive | Printing the HTML to PDF at the page size the CSS declares. The helper uses Playwright's Chromium; any browser the agent can drive with a print-to-PDF call does the same. Without one, deliver the HTML and say the PDF is printed from the browser's print dialog with background graphics on. |
| A PDF rasterizer or a page screenshot | The contact sheet for the review: PyMuPDF renders pages to PNG; a browser screenshot of each page does as well. |
| The organization's design tokens | Colors and the font family, read from the organization's brand file, a previous deck or its website, and written into the deck file's `theme`. Without any, the neutral defaults in [layout.md](references/layout.md) apply and the delivery says so. |

Check the shell and the browser before the first message. Nothing here costs money.

## Inputs

| Input | Source |
|---|---|
| Outline | The user's content: a document, a meeting plan, notes. Asked only when the request has nothing to draw on. |
| Audience | Derived from the outline: internal or external. External turns the house-style check on. |
| House style | The characters and patterns banned in the organization's external documents, from the request or the organization's own documents; asked once when the deck is external and nothing says. Written into the deck file's `style`. |
| Theme | Colors, font, logo paths: from the organization's files or a previous deck of the same tool; defaults otherwise. |
| Cover and closing | Client name, date, brand, contact lines: from the outline or the organization's files; the cover carries the client and the date, the closing the contact. |
| Output names | Derived: `<date>-<client>-<subject>` for all three files, in the folder where the organization keeps proposals, or next to the outline. |

## Workflow

### Phase 1: Read the outline into slides

Read the whole outline. For each slide the outline implies, decide its type and its blocks with the table in [deck-spec.md](references/deck-spec.md) "Choosing a block": three or fewer parallel items are cards, four to six are numbered rows, a sequence is a step stack, a schedule is a timeline, a system is a diagram, a list of things to decide is rows or a question list, a single sentence to remember is a banner, a caveat is a note. A slide holds at most two blocks plus a note, so that nothing has to shrink. Keep the outline's own words; do not add claims that the outline does not make.

Produce the slide plan: one line per slide, title and block types, and show it (checkpoint).

### Phase 2: Write the deck file

Write the deck file as [deck-spec.md](references/deck-spec.md) defines it: `meta` (client, date, brand, logo paths, `external`, `style`, `theme`), then `slides`. The cover and the closing are their own types. Every string in the file is final presentation text: full sentences where the slide speaks, short labels where it names. When the deck is external, write with the house style from the start; the check in phase 3 is a net, not the editor.

### Phase 3: Render and check

Run the helper, or write the HTML by hand from [layout.md](references/layout.md):

```
python scripts/render.py <deck.json> <out.html> --pdf <out.pdf>
```

The helper refuses to render an external deck that fails the style check and lists each offending string with its path in the file; fix the deck file and run again. It prints one HTML file with every slide as a page of the declared size, the theme inlined and the logos embedded, and then prints the PDF with the browser at that size with backgrounds on.

### Phase 4: Review the contact sheet

Rasterize every page at a small size and tile them into one image, look at it, and then at any page that looks wrong at full size. Fix in the deck file and render again until these hold:

- No block overflows its page and no text is cut; a slide that overflows loses a block to a new slide rather than shrinking.
- Every slide has the title the plan gave it, the cover and the closing are present, the page count matches the plan.
- The diagram's arrows point from the sources to the center and from the center to the outputs; the labels are readable.
- Nothing on the slides is a placeholder, except a screenshot frame the outline asked for.

Show the contact sheet (checkpoint).

### Phase 5: Deliver

Deliver the three files by path, the slide count, and the house-style verdict. Say what was derived (theme source, slide types chosen) and what the designer would take over (the diagram, the timeline shapes, the cover). Leave the deck file with the outputs: the next change is made there.

## Hard rules

- Content comes from the outline. No figures, names, prices or promises that the outline does not contain; where the outline is silent, the slide stays silent or says what is still to be confirmed.
- A deck for people outside the organization passes the declared house-style check before it is delivered, and never carries another party's document text, screenshots or prices unless the outline supplies them for that purpose.
- The HTML and the PDF are rendered from the deck file, never edited by hand; every change goes through the deck file.
- The contact sheet is looked at before the delivery. A render the agent has not seen is not delivered.
- Nothing is generated by a model and nothing is spent.

## Terminology

- **Deck file**: the JSON that holds the whole deck, `meta` and `slides`; the single source the files are rendered from.
- **Block**: one unit of a content slide's body: cards, banner, bullets, rows, stack, timeline, qa, split, diagram, note.
- **House style**: the characters and patterns the organization bans in external documents, declared in `meta.style` and checked before rendering.
- **Contact sheet**: one image tiling every page of the PDF at a small size, for the review.
- **Theme**: the colors, font and logos the renderer uses, declared in `meta.theme`.
