# Finding a skill in this pack

This pack holds skills for an AI agent to do real company work, one area at a time, each driving a real tool from the request to the finished result. An agent that has connected and holds a request needs to answer one question before anything else: is there a skill for this job, and which one? Ask it for work of the kinds the areas name, even where the material is at hand or in another connection (a question about a pack of documents connected beside this one, the notes of a meeting): the skill holds the checks that doing the job directly skips. A request that a line of chat answers (a sentence translated, a word explained) is not such work: answer it, with no search and no word about skills. This page says how the pack is laid out, the three ways to find a skill, how a result is read, and what to do when nothing fits. The pack's words are English.

## How the pack is laid out

- **An area is who does the work.** `marketing/`, `media/`, `design/`, `engineering/`, `product/`, `operations/` and `writing/` are the folders, one per kind of work, each with a manifest that says who its skills are for, a `README.md` that lists them, its skills under `skills/` and the documents its people read under `docs/`. The connection instructions introduce the areas with a line each, the kinds of work first, as far as their room allows, and name the pack's manifest (`SKILLCDN.md`, the rules every skill runs under) and its README as what to read on demand; `browse_repo` on the root lists every area, and on a folder names the folder's own manifest.
- **A skill's name is its tool family and its job.** `<area>/skills/<tool>-<job>/`: `higgsfield-shorts-ad` is the Higgsfield tools making a shorts ad, `html-card-news-from-brief` is HTML rendering a card news post from a brief, `skillcdn-document-research` is SkillCDN itself researching a pack of documents, `meta-ad-library-creative-research` is the Meta Ad Library website read for ad creatives. Read a name as "with this tool, this job"; the words are hyphenated one by one so that a search matches each of them.
- **A document set is not a skill.** `docs/<family>/` at the root and `<area>/docs/<family>/` hold what the skills of one tool family share (how a browser behaves, what the Higgsfield tools do, the shape of a card news brief); `docs/pack/`, this set, is about the pack itself. A search returns them as `document:` results beside the `skill:` results.

## Three ways to find a skill

1. **The jobs index, first.** [`jobs.md`](jobs.md) has one section per job, under a heading per area, headed by the sentence a user says, with the skill's path; every skill of the pack has its section there. Search it with the job's words scoped to this set (`search_repo` with `path` set to `docs/pack`), or read it whole with `read_repo_file`; a section that matches names the skill, and the skill's path goes to `load_skill` as it is.
2. **Browse by area.** When the request says what kind of work it is, `browse_repo` on `<area>/skills` lists every skill of the area with its description, and the description's first lines say what the skill makes and when to use it. Two areas take two calls.
3. **Search the whole pack.** `search_repo` with two or three English nouns of the job, the way a user would name it ("card news post", "slides from notes", "payments on the site"), not a sentence of instructions. The pack's words are English: a request in Korean, Japanese or any other language is translated to the English words first (카드뉴스 is "card news", 발표자료 is "slides" or "deck", 광고 is "ad", 결제 is "payments", 핸드북 is "handbook"); the translations a skill carries are for people and are not searched. How the ranking works, so that the words are chosen well: a word that few entries hold decides the order and a word every entry repeats decides next to nothing, so the distinctive noun of the job matters most; a match in a skill's name counts twice a match in its body, a match in a heading of a document counts between the two, and a hyphenated name is matched by its parts as well as whole; a skill counts only a little above a document (its score 1.05 times a document's, since SkillCDN 0.5.1), so a document that matches better can stand above it, and the jobs index, which names the skill, is often the second result: take the path it gives; where the deployment searches by meaning as well, a question asked in other words still finds the passage, and the result's last line says so (`Ranked by words and meaning.`). When that line says `by words alone this time`, ask once more with other words for the same job before concluding.

## Through a console

An agent that reads this pack through a SkillCDN Console's command, and not through a connection of its host, has the same four reads as commands: `search_repo` is `console skills --search <words> --limit 5 [<folder>]`, `load_skill` is `console skill <path>` (the skill's folder or its `SKILL.md`), `read_repo_file` is `console skill --file <path>`, and `browse_repo` on a folder is `console skills <folder>`. A skill is found by the search, a few hits at a time; `console skills` alone lists the whole pack, which is long, and is for looking around. What is longer than one command's output comes in pages that say how to go on, so take a command's output whole, with no `head`, `tail` or filter behind it: a file says at its head the `--offset` it continues at, a folder ends with the `nextCursor` that `--cursor` takes, and a part of a skill ends with the command for the next part, alone on its last line. Run that one, and the one after it, until a part says `Skill context is complete` (`The skill is complete` before console 0.6.1), before acting on any part, a plan included; a skill that came whole says neither. A path is the same either way, and everything on this page and in the skills holds as written.

## Reading a result

- A `skill:` result names the skill's path and its description: load the path with `load_skill` and follow it to the end before applying it. A `document:` result is a page with the sections that matched; it may name the skill (the jobs index does), and it is never run as one. A result marked as the overview of its folder is that folder's `README.md`, the map that says a little of everything in it: go on to the page it names rather than answering from the map.
- A description says what comes out from what, then when to use the skill in the user's own phrases ("Use when a user says ..."), and, where a neighbouring skill does a job that looks alike, which one to use instead. Read that last sentence before choosing between two.
- A skill result that says `described only` is served without its content under its license; its source link says where to read it.

## When no skill fits

Say so plainly: there is no skill in this pack for this job. Name the nearest skill and what it would not do, so that the user can decide whether a part of the job is still worth it; do not stretch a skill past what its description says, because its checkpoints and verdicts are written for its own job. Where the work has been done once by hand, in this session or another, `skillcdn-skill-authoring` (engineering) turns it into a skill in a fork of this pack or in this one. What the pack plans to add next is kept in its guide on the git host, which the mount does not serve.
