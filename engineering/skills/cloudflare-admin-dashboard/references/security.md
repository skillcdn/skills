# The security design

What the admin protects against, and how each protection is built in rather than configured: the separate Worker, Access and the guard, the operators' allowlist, the secrets and their permissions, requests that change something, the headers, the audit log, what pages and messages may contain, and what the inventory looks for in the public site. The Access facts are in [access.md](/engineering/docs/cloudflare/access.md); this page is the design.

## The threat model

The admin shows the business's money and customers and can refund, pause ads and change budgets. Whoever opens it holds the business. The attacks that matter: a leaked or guessed password; a stolen cookie; a script injected into the public site running with the operator's rights; a forged request from another site; a link in a chat message that opens a customer's content; a leaked key that can do more than read; an action nobody can trace; an operator's mistake with no confirmation; an admin left open because a setting was missing. The requirements that follow: no shared password, no session on the public origin, no default key when a secret is missing, a rate limit on every entry, an audit of every action, no link that opens a customer's page, no pixel on the admin, and no switch that unlocks paid content. Each is met here by construction.

## One Worker of its own

The admin is `admin/` in the same repository, a Worker named `<project>-admin`, with its own Wrangler configuration, its own secrets and its own address, bound to the same D1 database by id. The public site's bundle holds no admin code, its cookies never reach the admin's origin, a script injected into a public page runs where no admin session exists, and the admin's keys are not in the public Worker's secrets. The admin's own address is on `workers.dev` (or `admin.<domain>` later), which the per-Worker Access setting covers whole. The database is shared, so a compromise of the public site can read and write the admin's tables; the admin therefore keeps no secret in the database, and its audit log is mirrored to the Worker's logs (below).

## Access, then the guard

Access authenticates: the operator's email, a code sent to it, a session of a day at most, Cloudflare's logs. The Worker authorizes: on every request, the guard verifies `Cf-Access-Jwt-Assertion` against the team domain's keys with RS256, the issuer and the audience, reads the `email` claim, and checks it against the operators' allowlist. It fails closed:

| Condition | Answer |
|---|---|
| `ACCESS_TEAM_DOMAIN` or `ACCESS_AUD` unset, or `ADMIN_OPERATORS` empty | 503, a one-line page "admin not configured", nothing else, every route |
| No header, or a token that fails verification | 403, a one-line page, nothing else |
| A verified token without an `email` claim (a service token) | 403, unless the route is one the plan opened to a service token |
| A verified `email` not in `ADMIN_OPERATORS` | 403, and an audit row naming the email |
| Local development only: `ENVIRONMENT` is not `production`, `ADMIN_DEV_BYPASS` is `1`, and the request URL's hostname is `localhost` or `127.0.0.1` | The actor is `dev@localhost`; the three conditions come from `admin/.dev.vars`, which `wrangler dev` reads and a deploy never does, and the production configuration sets `ENVIRONMENT` to `production` as a var, so that a deployed Worker with no secrets answers 503 to every request, loopback or not |

`ADMIN_OPERATORS` is a secret of the Worker (comma-separated emails, the same list as the Access policy, which uses the "Emails" selector and never a whole domain), kept out of the repository because a public repository would publish the addresses that receive the login codes; removing an operator from the policy or from the list each suffices. There is no password, no cookie the Worker sets for authentication, no session table, no fallback key. Logging out is Access's own `/cdn-cgi/access/logout` on the team domain, linked from the header. The audit log keeps a removed operator's past actions.

## Secrets and variables, least privilege

| Name | Kind | Holds | May do |
|---|---|---|---|
| `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD` | Secrets | The issuer (`https://<team>.cloudflareaccess.com`) and the audience | Nothing by itself; without them the admin is closed |
| `ADMIN_OPERATORS` | Secret | The operators' emails | The allowlist the guard checks |
| `ADMIN_CONFIRM_SECRET` | Secret, 32 random bytes generated by the deploy skill's secrets path | The confirmation tokens' key | Signing a confirmation; never derived from anything public, never in the database |
| `STRIPE_READ_KEY` | Secret | A restricted key with Balance Transactions Read, Charges Read, PaymentIntents Read, Webhook Endpoints Read | Read the settled revenue ledger and the endpoint's status |
| `STRIPE_REFUND_KEY` | Secret, only when the plan has the refund control | A restricted key with Refunds Write and PaymentIntents Read | Issue a refund, nothing else |
| `META_ADS_ACCESS_TOKEN`, `META_AD_ACCOUNT_IDS` | Secrets | An `ads_read` employee system user token and the account mapping | Read insights and campaign status |
| `META_ADS_MANAGE_TOKEN` | Secret, only when the plan has the ads controls | An `ads_management` token | Pause, resume, re-budget |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | Secrets | The chat | Send the digest and the alerts |

None of the public site's secrets (its session signing key, its payment runtime key, its dataset tokens) is set on the admin, and none of the admin's is set on the public site. The admin's `admin/.dev.vars.example` lists its names with comments; the deploy skill's secrets path sets them; the system panel shows which are set, never a value or a prefix.

## Requests that change something

A change is a `POST` to a route under `/actions/`, never a `GET`. Each passes four gates: the guard (above); the origin check (a present `Sec-Fetch-Site` header must be `same-origin`; when it is absent, the `Origin` header must equal the admin's own origin; both absent is 403); the confirmation token (an HMAC with `ADMIN_CONFIRM_SECRET` over the action, its parameters, the actor and a nonce, valid ten minutes, embedded in the confirmation page; the nonce is consumed by an `INSERT` into a table keyed on it before the action runs, so that a replay, an altered parameter or two concurrent posts fail); and the cap (a refund at most the order's unrefunded amount and at most the plan's daily refund total, in the order's currency's minor units; a budget step at most the plan's percentage and under the market's daily cap; a pause and a resume unbounded). The confirmation page shows the exact effect in plain words ("Refund 10 USD of order ... to the card; the unlock is removed when the site's webhook sees the refund") and the one button. The result, success or failure, is written to the audit log and shown.

## Headers and responses

Every response: `Content-Security-Policy: default-src 'self'; img-src 'self' data:; style-src 'self'; script-src 'self'; frame-ancestors 'none'; form-action 'self'; base-uri 'none'`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `X-Robots-Tag: noindex`, and `Strict-Transport-Security` once the admin serves on a custom domain. No third-party script, font or style; the admin's own stylesheet and a small script of its own for the few interactions. Every value from the database or an API is rendered through the template engine's escaping, never as raw HTML (no `raw()`, no `dangerouslySetInnerHTML`), because customer emails, campaign names and metadata are attacker-controlled text. Charts are inline SVG built from numbers. Search inputs are bound as parameters, with `instr()` for "contains" because D1 refuses `LIKE` patterns over 50 bytes; page numbers out of range go to the last page.

## The audit log

```sql
CREATE TABLE admin_audit (
  id TEXT PRIMARY KEY, at TEXT NOT NULL, actor TEXT NOT NULL,
  action TEXT NOT NULL, target TEXT, params TEXT, result TEXT, ok INTEGER NOT NULL
);
CREATE INDEX idx_admin_audit_at ON admin_audit(at);
CREATE TABLE admin_nonces (nonce TEXT PRIMARY KEY, used_at TEXT NOT NULL);
```

Written by every action, by every sync (actor `cron`), by every automated rule, by a refused email, and by a sign-in seen for the first time in a day (actor, action `signin`). Each row is also written as one JSON line to the Worker's logs, which the shared database cannot alter. Never deleted by the admin. The system panel lists it newest first with a filter by actor and action.

## What a page or a message may contain

A page shows a customer's email and order amounts to the operator, because that is the operator's job, but never a session cookie, a key, a token or a prefix of one, and never a link that opens a customer's content without the customer's own sign-in: an order's payment is linked to Stripe's dashboard page by its PaymentIntent id (which opens only for a signed-in Stripe user), never to a receipt URL; a "view as customer" link is a bearer link and is left out, or opens a read-only rendering inside the admin. A chat message carries figures and the admin's own URL and nothing that unlocks anything; link previews are off. The admin sets no analytics and loads no pixel. Customer-identifying search terms stay out of the URL (search is a `POST` that renders the list) so that no log or browser history keeps them. The chat tool's bot token is part of its request URL by the tool's design; the sender never logs that URL or a raw error object, and a test asserts that no log line contains a secret.

## What the inventory looks for in the public site

Reported to the user as findings, fixed only on their word, because they are the public site's code: an environment switch that unlocks paid content or bypasses a payment, a password-protected admin page still present (removed when the new admin replaces it, on the user's word), a signing key with a fallback value in the source, a cron or internal route authenticated by a plain comparison (made constant-time), pixels loaded on private pages, admin keys in the public Worker's secrets, and secrets listed as optional in `DEPLOY.md`.
