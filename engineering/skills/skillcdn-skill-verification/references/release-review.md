# Release review: a service shipped a version

When SkillCDN, the console or another service the skills state facts about ships a version, the change under the skills is the service's own. The review covers every skill and shared page that states how the service behaves; its findings are the sentences the release made stale, folded in by phase 5 with the version and the month, and the fresh run goes to the skill the release changes most.

1. **Read the release**, the changelog entries between the two versions and the diff of the specifications and the author guides. For SkillCDN: `packages/*/CHANGELOG.md` and `docs/specs/*.md` of its repository between the two tags, or the release notes on the git host. For the console: its package's changelog, `docs/specs/*.md`, and `skills/working-the-board/references/the-sentence.md`, which holds the sentence a bound checkout carries; its rules change with its version and are read with `console rules`.
2. **Run the released command over the checkout** where the service has one (`npx @skillcdn/cli@latest check`): a line, a note or a diagnostic it did not print before is the release as this pack meets it.
3. **Find the sentences.** Read every sentence that says what a tool answers, a check prints or a route returns, and search the whole checkout, the READMEs and the guide among it, for each thing the release names: a command, a field, a printed line, a number, a version. One fact is said on several pages, so a page that was brought up to date is no sign that its siblings were. Run every command a page shows against the released version where it only reads, the examples in a README first, since one that was never run stays wrong through every release.
4. **List each sentence** the release contradicts, dates or extends, with its file, its line and the version, a rule of the format that a skill restates in its own form among them. A sentence that only copies a number or a printed line the service may change again is cut to what an agent does with it, and the standard's page is linked.
5. **Have a fresh reader do the same** in the dry read, whose brief asks for stale statements first ([dry-read.md](dry-read.md) "The brief for a change"); where the two lists differ, the checkout decides.
