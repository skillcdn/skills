# Serving: from a push to what an agent gets

How a repository in the SkillCDN Format becomes what an agent is served: which branch, which commit and how to see it, how long it takes, what each way of receiving a skill brings with it, and the two checks that show what an agent will be told. Read before a push, and before a fresh agent loads what was pushed.

## The default branch is what is served

SkillCDN serves the repository's default branch, so a push to it is a public release (a private repository's, a release to the people the git host shows it to, who reach it signed in or with a token the deployment issued), and nothing in a checkout, committed or not, reaches an agent until it is pushed and served. A fork is served at its own address in the same way. An address that pins a commit (`skillcdn.ai/gh/<owner>/<repo>@<commit>`) keeps serving that commit whatever is pushed later; an index nobody has read for the deployment's retention time (30 days by default) is removed, and the pinned address answers `indexing` on its next request until it is built again (SkillCDN 0.5.0, checked 2026-11).

## Which commit an agent gets

- On the connection: `browse_repo`, `load_skill` and `read_repo_file` name the served commit in their `Source` line, as `Source: <owner>/<repo> (commit <short sha>)`. While the branch's newest commit is not the one served, the line carries one clause more: `newest <commit> indexing` while its index is built, `newest <commit> failed (<code>)` when it could not be, and `being reindexed` while the same commit is rebuilt under newer reading rules; the mount then answers from the last indexed commit of the branch, so an agent that loads a skill meanwhile gets the previous text (SkillCDN 0.5.1, checked 2026-11). The instructions an agent received when it connected name the commit served at that moment and are not refreshed; a later call's `Source` line names the current one (checked 2026-10).
- Over HTTP: `https://skillcdn.ai/api/v1/mounts/<address>`, the address without the host (`gh/<owner>/<repo>`; `gh/skillcdn/skills` for this pack), returns the mount's `commit` (the commit it answers from), `newest` (the branch's newest commit with its `status`, `indexing` or `failed`, and its `errorCode`, while another is served in its place; `null` when the served commit is the newest), its `index.status` (`ready` when the skills can be loaded), `index.search` (whether the mount is searched by meaning as well as by words, and how far its embedding has come), the counts of skills and documents, `index.groupCount` (how many top-level folders hold something, from SkillCDN 0.5.3), and the diagnostics when there are any (SkillCDN 0.5.1, checked 2026-11); a private repository's route answers only a request that carries an access token the deployment issued, as a bearer token, and `404` otherwise, as if the name were nothing.
- Against the checkout: `git rev-parse HEAD` and `git status` say what is local; `git diff <served commit> HEAD -- <paths>` says whether what an agent gets differs from the checkout for a skill's directory, the manifests above it and the shared pages it reads; `git show <served commit>:<path>` prints a file as it was at the served commit.

## How long serving takes

A push to the default branch is served once the deployment has looked the branch up again and indexed the new commit. Where the deployment runs a worker that indexes ahead of requests, a push its GitHub App announces is indexed within about a minute and the time its index takes, with nobody asking; otherwise the branch is looked up again when a request finds its last look-up older than `REF_TTL_SECONDS` (60 seconds by default), or by the worker every `INDEX_AHEAD_MINUTES` (15 by default) for a repository the operator lists; the indexing takes a minute or a few (SkillCDN 0.5.0, checked 2026-11). A release with new reading rules rebuilds a commit's index when the commit is next asked for and serves the one it has meanwhile, the `Source` line saying `being reindexed`. Until then the mount keeps answering from the last indexed commit and says so in its `Source` line and in `newest` (on the hosted service, a push was answered from the previous commit with `newest` naming the pushed one as `indexing` for a few minutes, 2026-10-26), so read the mount route before a fresh run rather than assuming the push is served; and read `git status -sb` first, because a commit that was never pushed looks the same from the mount, with `newest` still `null`. Check about once a minute, from a background command that polls the route or between other work, since a host may block a foreground sleep (Claude Code does, checked 2026-10); a `newest` that says `failed` names the code to fix, and one that still says `indexing` after ten minutes is reported. Do not push again while an agent is loading a skill: `load_skill` continues a long skill with a cursor into the served commit, and the cursor stops matching once another commit is served.

## What each way of receiving a skill brings

| The agent receives the skill through | It gets |
|---|---|
| The connection at the repository root | The rules of the manifests above the skill, the skill, and the files its `skillcdn.include` lists (its own references, and the shared pages named by their root-relative paths) in `load_skill`; any other served file with `read_repo_file` |
| The connection at an area | The same, except that `read_repo_file` reads only inside the area: a page of the area's `docs/` can be read, a page of the root `docs/` only when the skill includes it |
| The connection at one skill | The rules, the skill and its included files; nothing it only links outside its directory |
| The MCP skills extension | Each `SKILL.md` as a plain Agent Skills document with the rules and the included files inside, with a digest per file; a host without `read_repo_file` reads no linked page |
| The area's Claude Code plugin | The area's `skills/` and `docs/` as files, without the rules of the manifests and without the root `docs/` |
| The REST listing (`GET /api/v1/listing/<address>`, `?uri=` for one item; SkillCDN 0.4.2) | What the skills extension gives, as data: each `SKILL.md` assembled with the rules and the included files, every file with its digest, for a program that installs skills into an agent's own folder |
| A copy of the skill's directory | That directory alone |

A skill's Requirements say which of these lack what it reads, and where to fetch it. A change to a manifest or to a shared page a skill includes changes the served digest of every skill below the manifest or including the page, so a host that verified those skills through the extension asks its user again.

## The two checks

- `node scripts/check.mjs` in the checkout: the repository's own check of the manifests, the front-matter, the catalogs, the links, the includes and the text, the one its CI runs. It prints `ok:` with the counts when it passes, and each problem when it does not.
- `npx @skillcdn/cli@latest check` in the checkout: the indexer's own reading, with the parser and the limits the service uses. Name `@latest`: without it `npx` runs whichever copy its cache holds, and an older one reads the pack by older rules without saying so. It prints the version of the reading rules it applied, what an agent is told on connect with its length against the 2,000 characters the instructions hold (and, beside the length, whether the folder lines were shortened or some left out), each skill's license, the shared pages it includes, its size as served and whether the skills extension lists it, every document with how many sections its headings make and whether it is too large to be searched, and `ok: no index diagnostics` when it passes. It also reports as index diagnostics a local link that names no file of the repository, a link whose fragment names no section of its file (`fragment_not_found`), a picture without alternative text, a picture or an original that is not there, a document's `source` written like a path that names no file, a skill's reference to a file that is not text, and, for a document marked `derived` (a note or a glossary made from the pack), a quotation not found in the section its link names (`quote_not_in_source`), a block quote without that link (`quote_without_link`) and a `derived.from` that names nothing (`derived_from_missing`); under a `Notes:` heading it names, without failing, a section longer than one read carries (`section_large`). A document's link to its own original or picture is what the format asks for and is not reported (version 0.5.3 of the command, reading rules version 19, checked 2026-11). It needs npm, the network and the Node.js version the package asks for (24 or newer; on Node.js 22 it ran, with an engine warning when it was installed, checked 2026-11).
