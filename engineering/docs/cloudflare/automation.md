# Automation: what the token does and what a person does once

What an agent with the token does by itself (resources, secrets, deploys, domains, builds, analytics) and the few steps only a signed-in person can take in the dashboard, with the command or call for each. An agent does everything in the first table before asking for anything in the second. Commands and endpoints are as the Wrangler reference, the `cf` help and the API reference gave them when checked (Wrangler 2026-10, `cf` 2026-11); `npx wrangler <command> --help`, `npx cf <command> --help` and the API reference at `developers.cloudflare.com/api/` are the source when one has moved. Every path below is under `https://api.cloudflare.com/client/v4`, with the token as a bearer header.

A project has one of two configuration generations ([platform.md](platform.md) "The configuration file"): a Wrangler file, whose CLI is Wrangler (`npx wrangler`), or the typed `cloudflare.config.ts`, whose CLI is `cf` (the project's dev dependency, `npx cf`; in beta, so its commands carry the month they were checked, and `npx cf cli search "<the task in plain words>"` finds one that moved, `--help` on the match lists its options, and `--dry-run` prints the request without sending it; checked 2026-11). Each row gives the Wrangler form and the `cf` form. `cf` takes the ids the API uses where Wrangler takes names, and prints JSON on standard output; both read `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` from the environment.

## What the agent does with the token

| Need | How |
|---|---|
| Account id, zones | `GET /accounts`; `GET /zones?name=<domain>` (the zone id and `status`) |
| The `workers.dev` address | `GET /accounts/<id>/workers/subdomain` answers `result.subdomain`; the Worker's address is `https://<name>.<subdomain>.workers.dev`. An empty result means the account has none: `PUT /accounts/<id>/workers/subdomain` with `{"subdomain":"<chosen>"}` registers one (Workers Scripts Edit; checked 2026-10) |
| A database | Wrangler: `npx wrangler d1 create <name> --binding DB --update-config --location <hint>` (`apac`, `weur`, `eeur`, `wnam`, `enam`, `oc`: the region nearest the users, from the brief); schema: `npx wrangler d1 migrations create <name> <message>`, then `npx wrangler d1 migrations apply <name> --remote` (`--local` for dev); ad hoc: `npx wrangler d1 execute <name> --remote --command "<sql>"`; `npx wrangler d1 list`, `d1 info <name>`. `cf`: `npx cf d1 create --name <name> --primary-location-hint <hint>`, whose JSON result carries the `uuid` that goes into `bindings.d1({ name, id })` of the configuration by hand (no flag writes the file; `cf deploy` provisions a database for a binding without an id and writes nothing back, checked 2026-11); schema: `npx cf d1 migrations create <message>`, then `npx cf d1 migrations apply <database id> --dir ./migrations` (remote; `--local` for dev; the id only, never a name or a binding; the bookkeeping table is Wrangler's, so a project may move between the two); `npx cf d1 migrations list <database id>`; ad hoc: `npx cf d1 query <database id> --sql "<sql>"` (several statements joined by semicolons run as one batch; a file goes in as `--sql "$(cat <file>)"`, or as `--batch @<json>` when it is large); `npx cf d1 list`, `cf d1 get <database id>` |
| A bucket | Wrangler: `npx wrangler r2 bucket create <name> --binding BUCKET --update-config`; public files: `npx wrangler r2 bucket domain add <name> --domain files.<domain> --zone-id <zone id>`, or `dev-url enable` for a temporary `r2.dev` address. `cf`: `npx cf r2 buckets create --name <name> --location-hint <hint>`, the name into `bindings.r2({ name })`; a public domain through `cf r2 buckets domains custom`, the temporary `r2.dev` address through `cf r2 buckets domains managed` (their `--help`; not run, 2026-11) |
| A key-value namespace | Wrangler: `npx wrangler kv namespace create <NAME> --update-config`. `cf`: `npx cf kv namespaces create --title <name>-kv`, the result's `id` into `bindings.kv({ id })` (the typed binding carries no name, so the title is how the namespace is found again) |
| Secrets | A JSON file outside the repository `{"NAME":"value"}` (a key set to `null` deletes). Wrangler: on a Worker that exists, `npx wrangler secret bulk <file>`; on one never deployed, `npx wrangler deploy --secrets-file <file>` sets them with the first version; `npx wrangler secret list` to confirm names. `cf`: `npx cf deploy --prebuilt --secrets-file <file>` sets them with the version it uploads, first or later (JSON or `.env` lines); `npx cf workers secrets list --worker <name>` to confirm names; a change of several on a Worker that exists: `npx cf workers secrets bulk --worker <name> --secrets @<file>` in the API's own shape (`cf schema workers secrets bulk` prints it), which makes one new version from the active code and deploys it, as Wrangler's `secret bulk` does; one value: `npx wrangler secret put <NAME> --name <name>`, which reads it from standard input and works beside `cf` (`cf workers secrets update` takes the value as an option, which puts it on the command line; checked 2026-11). In a typed configuration every secret the code reads is declared in `worker.env` as `NAME: bindings.secret()` (platform.md). Delete the file |
| Deploy | Wrangler: the project's build script, then `npx wrangler deploy`; on a scaffold whose `deploy` script is the framework's own deploy wrapper (vinext's `vinext-cloudflare deploy`, which on the 2026-10 scaffold deployed with `--config dist/server/wrangler.json`, the configuration the build generated, rebuilds unless `--skip-build` is passed, and takes no secrets flag), the deploy is `npm run deploy -- --skip-build` after the build (Workers Builds runs the same), a deploy that carries secrets is `npx wrangler deploy --config dist/server/wrangler.json --secrets-file <file>`, and a preview is `npx wrangler preview --config dist/server/wrangler.json` (a preview binds the production database and carries no production secrets). Then `npx wrangler deployments status` (the active version id), `npx wrangler versions list`, `npx wrangler rollback`. `cf`: the build script (`vite build` writes the Build Output to `.cloudflare/output/v0/`), then `npx cf deploy --prebuilt` (`--secrets-file <file>` when secrets go with the version; `--dry-run` builds and validates without credentials; without `--prebuilt`, `cf deploy` builds through the framework's own command, never through the `build` script); on a scaffold whose `deploy` script is the wrapper (the same `vinext-cloudflare deploy`, which deploys through `cf` on a typed project, checked 2026-11), `npm run deploy -- --skip-build` after the build is the deploy without secrets, which Workers Builds runs too. Then `npx cf workers deployments list --worker <name>` (the first entry serves traffic), `npx cf workers versions list --worker <name>`; a rollback is `npx cf workers deployments create --worker <name>` with the earlier version at 100 percent (`--help` gives the `--versions` shape) or the dashboard's Deployments tab; a preview is `npx cf previews deploy --prebuilt` after a build, named after the branch unless a name is passed (not run, 2026-11) |
| Logs | `npx wrangler tail <name>` live, on both generations: `cf` has no live log command yet, and Wrangler, which does not read `cloudflare.config.ts`, takes the Worker's name (checked 2026-11); Workers Logs in the dashboard when observability is on |
| A zone for a domain the user owns | `POST /zones` with `{"name":"<domain>","account":{"id":"<account id>"},"type":"full"}`; the result's `name_servers` go to the user, who sets them at the current registrar; `status` turns `active` once they resolve |
| A new domain | Registrar API, beta (checked 2026-10): `GET /accounts/<id>/registrar/domain-search?q=<words>`, `POST /accounts/<id>/registrar/domain-check` with `{"domains":[...]}` for the live price, `POST /accounts/<id>/registrar/registrations` with `{"domain_name":"<domain>"}`; a `202` is polled at `.../registrations/<domain>/registration-status`; `extension_not_supported_via_api` means the dashboard. The domain uses Cloudflare nameservers, so its zone is active at once |
| DNS records | `POST /zones/<zone id>/dns_records` with `{"type":"TXT","name":"<name>","content":"<value>","proxied":false}`; `GET` to list |
| The app on its domain | `routes: [{"pattern":"<domain>","custom_domain":true},{"pattern":"www.<domain>","custom_domain":true}]` in a Wrangler configuration, or `domains: ["<domain>", "www.<domain>"]` under `worker` in `cloudflare.config.ts`, then deploy; Cloudflare creates the records and the certificate; the app redirects `www` to the apex, or a Single Redirect rule does. The `workers.dev` address goes off with `workers_dev: false` in a Wrangler file, or, since the typed configuration has no such key (checked 2026-11), with `POST /accounts/<id>/workers/scripts/<name>/subdomain` and `{"enabled":false,"previews_enabled":true}` (Workers Scripts Edit) |
| Deploys on push: the connection | After the GitHub App is installed (below): GitHub ids from `https://api.github.com/users/<user>` and `/repos/<user>/<repo>` (`.id` of each); `PUT /accounts/<id>/builds/repos/connections` with `{"provider_type":"github","provider_account_id":"<user id>","provider_account_name":"<user>","repo_id":"<repo id>","repo_name":"<repo>"}`, keep `repo_connection_uuid`; the Worker's tag from `GET /accounts/<id>/workers/scripts` (`.result[].tag` for `.id` equal to the name); a build token from `GET /accounts/<id>/builds/tokens` (`build_token_uuid`; empty until a person made one in the dashboard, the second table). The Builds API takes a user token only; an account token answers "Invalid token" (checked 2026-10) |
| Deploys on push: the triggers | `POST /accounts/<id>/builds/triggers` with `{"external_script_id":"<tag>","repo_connection_uuid":"<uuid>","build_token_uuid":"<uuid>","trigger_name":"Deploy production","build_command":"npm run build","deploy_command":"npx wrangler deploy","root_directory":"/","branch_includes":["main"],"branch_excludes":[],"path_includes":["*"],"path_excludes":[]}` (the deploy command the Deploy row gives for the project: `npx wrangler deploy`, the wrapper with its skip flag where the `deploy` script is one, else `npx cf deploy --prebuilt` on a typed project; whether the build environment's credentials reach `cf` was not checked, 2026-11); the same once more for previews with `"trigger_name":"Deploy previews"`, `"deploy_command":"npx wrangler preview"` (the preview command of the Deploy row: with the wrapper's generated configuration on the 2026-10 vinext scaffold, `npx cf previews deploy --prebuilt` on a typed project), `"branch_includes":["*"]`, `"branch_excludes":["main"]`. Build variables: `PATCH /accounts/<id>/builds/triggers/<trigger uuid>/environment_variables` with `{"NODE_VERSION":{"value":"24","is_secret":false},"NEXT_PUBLIC_SITE_URL":{"value":"https://...","is_secret":false}}`. Existing triggers of a Worker: `GET /accounts/<id>/builds/workers/<tag>/triggers` (`trigger_uuid`, `trigger_name`, `branch_includes`); a field of one changes with `PATCH /accounts/<id>/builds/triggers/<trigger uuid>`. Run one: `POST /accounts/<id>/builds/triggers/<trigger uuid>/builds` with `{"branch":"main"}` (a build started this way records no `commit_hash`; the build a push triggers does, checked 2026-10); list: `GET /accounts/<id>/builds/workers/<tag>/builds` (status, `build_trigger_metadata.commit_hash`, the version it produced); log: `GET /accounts/<id>/builds/builds/<build uuid>/logs` |
| Analytics | `POST /accounts/<id>/rum/site_info` with `{"zone_tag":"<zone id>","auto_install":true}` for a zone that is this site's alone (the beacon is injected at the edge into every hostname of the zone), or `{"host":"<hostname>"}` for a `workers.dev` address or a hostname under a zone shared with other sites, where the returned snippet (`beacon.min.js` with the site's token) goes into the HTML, or its token into the build variable the layout reads; needs Account Settings Edit; `GET /accounts/<id>/rum/site_info/list` answered an authentication error with a token that could create a site (checked 2026-10) |
| Transactional email | Email Service: `send_email: [{"name":"EMAIL"}]` in a Wrangler configuration or `EMAIL: bindings.sendEmail()` in the typed one, and `env.EMAIL.send({...})`, or `POST /accounts/<id>/email/sending/send`; Workers Paid, beta (checked 2026-10) |
| A bot check on forms | Turnstile widget: `POST /accounts/<id>/challenges/widgets` (user token) |

## What a person does once in the dashboard

| Step | Where | Why the agent cannot |
|---|---|---|
| Create the API token | My Profile > API Tokens, or Manage Account > Account API Tokens ([tokens.md](tokens.md)) | A token is made by a signed-in person |
| Install the Cloudflare GitHub App | Workers & Pages > any Worker > Settings > Builds > Connect > GitHub, choose the account or organization, grant all repositories (or add the project's repository to the installation on GitHub once it exists), Install & Authorize (the Builds API reference's own prerequisite, checked 2026-10); with no Worker yet, Workers & Pages > Create application > Import a repository > Git account > + Add account does the same, and the page is left without importing. The installation shows at `github.com/settings/installations`, or `github.com/organizations/<org>/settings/installations` for an organization; the dashboard's labels follow its language, the order does not | A GitHub authorization that ties the GitHub account to this Cloudflare account; after it, every build setting is API. A user who followed the dashboard's prompts to the end (chose the repository, saved) has made the connection and the production trigger already: the agent lists them and adds only what is missing |
| Create a build token | The project's Worker (it exists after the first deploy) > Settings > Builds > API token > Create new token, named for the project | The Builds API lists tokens and cannot create one (checked 2026-10) |
| Add the R2 subscription | Storage & databases > R2 > Overview, complete the checkout (free tier, a billing profile) | A purchase flow, even at zero |
| Move to Workers Paid | Workers & Pages > Plans | A purchase |
| Prepare domain buying | Billing with a default payment method; a default registrant contact and the Domain Registration Agreement at `dash.cloudflare.com/<account id>/domains/registrations` (checked 2026-10) | Legal and billing consent |
| Point an existing domain at Cloudflare | At the current registrar: replace the nameservers with the two the zone call returned | Another provider's account |
| Enable Email Sending for a domain | Email Service pages for the account and the zone, as the Email Sending get-started page says | Plan and domain consent |
| OAuth client for Google sign-in | Google Cloud Console > APIs & Services > Credentials > Create credentials > OAuth client ID > type Web application; Authorized redirect URIs: `https://<address>/<callback path>` for the live address (and the domain, when it comes) and `http://localhost:<port>/<callback path>` for development; copy the client id and secret (path as of 2026-10). A regional provider (Kakao, Naver, LINE, WeChat, Zalo, VK: the market table in the new-app skill's auth.md): its developer console, with the same two values (a client id or key, and a secret) and the same two callback URLs; the console's menu names are taken from the provider's own documentation on the day, and the consent items are the fewest the sign-in needs (a name and a picture; an email only when the app uses it) | Outside Cloudflare |

Give each step as the exact clicks of the day, in one message, with what to send back (a token, a "done", nameservers set), and continue with everything that does not wait on it.
